# Governing Protocols (Rules)

1. **Protocol 1 (Rule 1) — Exhaustive Cross-Reference Against Historical Reference Codebases & Authoritative Master Documentation:** Every route, schema, component, hook, and layout must be thoroughly audited against the master specification documentation and historical reference codebases to understand domain boundaries, business logic, and past patterns before planning or code modification.
2. **Protocol 2 (Rule 2) — Zero Blind Copying of Historical Code; Zero Blind Acceptance of Requirements:** Validate every architectural pattern from first principles. Resolve bugs, security vulnerabilities, and technical debt from previous implementations while critically evaluating, challenging, and refining requirements where necessary.
3. **Protocol 3 (Rule 3) — Owner Review, Challenge, and Sequential Alignment:** Never silently accept ambiguous instructions or introduce speculative assumptions. Review, challenge, and align each entity sequentially with the project owner by providing logical reasoning, trade-offs, impact analysis, and clear recommendations.
4. **Protocol 4 (Rule 4) — Small UI Property Consistency:** Buttons, icons, chips, and form controls that accept size configuration must strictly use the small variant (`size="small"`) to preserve dense, professional visual hierarchy, clean interface density, and desktop ergonomics.
5. **Protocol 5 (Rule 5) — Breakpoint-Driven Grid Layouts (Never Use Raw Fractional Units):** Grid layouts must strictly use Material UI breakpoint size definitions (`size={{ xs: ..., sm: ..., md: ..., lg: ..., xl: ... }}`). Never use CSS grid templates with raw fractional (`fr`) units.
6. **Protocol 6 (Rule 6) — Zero Deprecated UI Component Properties:** Never use deprecated Material UI component properties (such as `classes`, `selected`, or `color="default"`). Sub-element customization, state styles, and variant overrides must strictly use system style properties (`sx`) or the slot and slot properties API (`slots` and `slotProps`).
7. **Protocol 7 (Rule 7) — Strict Theme Token Compliance:** All colors, elevation levels, typography hierarchies, border radii, and surface tokens must derive directly from the centralized theme system. Never hardcode raw hexadecimal colors, RGB strings, or inline CSS values; components must remain 100% theme-driven and responsive to active palette modes.
8. **Protocol 8 (Rule 8) — 1-to-1 Constants Parity Between Server & Client:** Route path definitions, validation constraints, sizing bounds, and enumeration dictionaries must maintain strict 1-to-1 parity between backend and frontend centralized constants files to prevent contract drift and ensure system-wide predictability.
9. **Protocol 9 (Rule 9) — Semantic Breakpoints (Zero Hardcoded Pixel Media Queries):** Responsive design must exclusively utilize framework breakpoint keys (`xs`, `sm`, `md`, `lg`, `xl`) and theme-aware media query helpers. Hardcoded pixel thresholds and custom CSS media query widths are strictly forbidden.
10. **Protocol 10 (Rule 10) — Extra-Small Screen Iconification (`xs`):** On extra-small screens (`xs`), UI actions and controls must collapse into icon buttons wrapped in accessible tooltip overlays; text labels and secondary metadata hide automatically to preserve clean, un-crowded touch targets and mobile ergonomics.
11. **Protocol 11 (Rule 11) — Modular React Building Block Architecture:** Maintain strict separation of concerns: clear component hierarchies, single responsibility per file, stateless presentation components decoupled from stateful containers, pure memoized components where appropriate, and strict property contracts.
12. **Protocol 12 (Rule 12) — Proven Baseline Preservation Without Speculative Bloat:** Preserve the full functional capability and clarity of historical baseline interfaces without introducing speculative scaffolding, premature abstractions, or unnecessary widget bloat.
13. **Protocol 13 (Rule 13) — Zero Typing Lag on Text Inputs:** All text fields, search bars, form controls, and composer inputs must utilize debounced local state or uncontrolled native references to guarantee zero-millisecond input latency and smooth 60fps typing responsiveness.
14. **Protocol 14 (Rule 14) — Elimination of Re-render Cascades:** Optimize rendering performance by memoizing callbacks, expensive derivations, and stable component trees. Never dismiss double-renders, performance bottlenecks, or unintended side effects by attributing them to developer-mode lifecycle checks.
15. **Protocol 15 (Rule 15) — Clean Accessibility & Zero ARIA Violations:** Eliminate accessibility traps, focus retention conflicts, and `aria-hidden` warnings when opening and closing modals, dialogs, drawers, and popovers. Ensure focus is properly blurred or restored and background surfaces are marked inert while overlays are active.
16. **Protocol 16 (Rule 16) — Decoupled State Architecture & Redux Zero-Conflict Boundary:** Global state management strictly governs REST API caching, authentication session identity, and navigational thread metadata. Global state does NOT own live streaming token deltas, active chunk accumulation, or typing buffers. Live conversation streaming must be owned exclusively by the dedicated local chat runtime context to prevent render cascades and input lag.
17. **Protocol 17 (Rule 17) — Silent Token Refresh & Single-Flight Mutex:** Enforce a dual-token authentication lifecycle using short-lived access tokens and long-lived refresh tokens delivered exclusively through secure, HttpOnly, SameSite cookies. All refresh requests must be serialized through a client-side single-flight mutex so concurrent unauthenticated responses wait on a single shared refresh operation, eliminating token rotation race conditions and false session invalidation.
18. **Protocol 18 (Rule 18) — Unified Validation Across Application Boundaries:** A unified schema validation library must be utilized across all server boundaries, HTTP middleware, structured agent outputs, and tool schemas to guarantee consistent error contracts and strict payload enforcement.
19. **Protocol 19 (Rule 19) — Formal Dependency Management & Cataloging:** Never modify package manifests manually. All package additions must be installed via the workspace package manager without specifying inline version flags. Every dependency must be formally documented with its exact resolved version, purpose, official documentation reference, license, and runtime compatibility.
20. **Protocol 20 (Rule 20) — Comprehensive JSDoc Annotations & Interface Contracts:** Every module, class, service, controller, middleware, hook, slice, and component created or modified must feature comprehensive JSDoc documentation, including type declarations, parameter descriptions, return contracts, and thrown exceptions.
21. **Protocol 21 (Rule 21) — Strict Single-User Isolation & IDOR Prevention:** Every server-side endpoint, service method, and database query must be strictly scoped to the authenticated user ID. Insecure Direct Object References (IDOR) are impossible: client-supplied user identifiers in query parameters or request bodies are ignored, and cross-user or nonexistent resource requests return uniform HTTP 404 responses.
22. **Protocol 22 (Rule 22) — Envelope-Encrypted BYOK Credential Protection at Rest:** User-supplied API keys and third-party connector tokens must be envelope-encrypted with authenticated symmetric encryption (AES-256-GCM) at rest in the database, excluded from default queries, and stripped from all client-facing data transformations.
23. **Protocol 23 (Rule 23) — Automated Quality Verification via Specialized Agents:** Every completed task and phase deliverable must be independently verified and confirmed 100% green by specialized audit and verification agents before presenting to the product owner for review.
24. **Protocol 24 (Rule 24) — Deterministic Vertical-Slice Functional Testing via REST Client (`.http` / `.rest`):** Automated test verification must be authored and maintained as REST Client specification files (`.http` / `.rest`) executing real end-to-end HTTP requests rather than isolated, artificial unit mocks. Every feature and workflow—including authentication, session lifecycle, message turns, agent processing, streaming, tool executions, document handling, and approvals—must be validated across the complete vertical slice: from live HTTP server entry through application middleware, route definitions, input validators, controllers, domain services, and agent state machines down to real database queries and response headers or cookies. Tests must define explicit assertions (status codes, payloads, headers) with variable chaining and cookie persistence, enabling interactive execution directly within the IDE via REST Client and deterministic headless execution via CLI test runners. Every related positive, negative, security, and edge-case scenario must pass deterministically without redundant or unnecessary tests. Frontend production builds and static linting must pass with zero errors and zero warnings.
25. **Protocol 25 (Rule 25) — Zero Commits Invariant (Explicit Owner Authorization Gate):** Never execute a git commit under any circumstance, even upon achieving 100% green test passes and complete implementation, until explicit product owner instruction. Staging and committing occur only upon explicit owner authorization.
26. **Protocol 26 (Rule 26) — Direct Adoption of Proven Historical Implementations (Zero Unnecessary Reinvention):** If a historical source implementation, layout, or provider structure functions cleanly, reliably, and without architectural or security defects, directly adopt and support that proven design rather than introducing speculative refactoring, alternative nesting, or unnecessary complexity. Engineering efforts must focus on resolving actual bugs, technical debt, and vulnerabilities, not reinventing what already functions soundly.
27. **Protocol 27 (Rule 27) — Universal Constants Centralization & Prohibition of Magic Literals:** Localized, module-scoped, or inline hardcoded magic literals are strictly prohibited across the entire platform. All configuration bounds, sizing dimensions, compression ratios, timeouts, regex patterns, route endpoints, storage quotas, and enumeration dictionaries must be defined in centralized constants modules and imported wherever needed.
28. **Protocol 28 (Rule 28) — Authoritative AI Model Identifiers & Deprecation of Phantom Endpoints:** AI foundation model identifiers across constants, schemas, selectors, and label mappings must strictly reflect the verified, supported models: Google Gemini models (`gemini-3.1-flash-lite` as Default/High Speed, `gemini-3.8-flash` as Pro/Deep Reasoning, and `gemini-3-flash-preview` as Fallback/Preview) and Addis AI (`addis-1` as the native Amharic Fidel foundation model). All legacy model generations (including `gemini-2.5-flash`, `gemini-2.5-flash-lite`, and `gemini-2.5-pro`) and nonexistent phantom endpoints (such as `gemini-3.5-flash`) are strictly prohibited. The native regional model (`addis-1`) must be fully selectable alongside Google Gemini models in user profile and conversational inference configurations.
29. **Protocol 29 (Rule 29) — Explicit Display Names for Forwarded References & Prohibition of Legacy Runtime Prop-Types:** Components wrapped with forwarded element references must explicitly declare a display name matching their component identifier to ensure transparent debugging, error boundaries, and tree inspection. The legacy runtime property validation package is strictly prohibited across all frontend modules; component interfaces must be documented exclusively via comprehensive JSDoc contracts.
30. **Protocol 30 (Rule 30) — Zero Unused Imports and Dead Tokens:** Every imported symbol across server and client codebases must be actively utilized in runtime logic or type contracts. Importing unused constants, models, schemas, or components is strictly prohibited. All code must pass dead-code analysis and static linting with zero dangling references before task completion.
31. **Protocol 31 (Rule 31) — Single-Source Utility Ownership & Prohibition of Controller Re-Exports:** Utility functions belong strictly to their designated shared utility modules. Request controllers, domain services, and routing modules must import utilities directly from their origin and must never re-export helper functions. Controllers must export request handlers exclusively to avoid circular references and leaky abstraction layers.
32. **Protocol 32 (Rule 32) — Minimal Registration Payload (Strict Email/Password Only):** Account registration request bodies accept strictly email and password credentials. Registration validation and handlers must never accept or expect first name, last name, organizational role, or avatar fields. User names are automatically derived from the email address upon registration, while supplementary personal profile metadata and settings are managed exclusively post-registration.
33. **Protocol 33 (Rule 33) — Toast-Driven Authentication Error Delivery & Clean Form Surfaces:** Authentication and authorization errors on public forms must be surfaced exclusively via non-intrusive toast notifications. Public login and registration surfaces must remain clean, minimal, and compact, featuring straightforward action buttons with zero persistent alert banners or intrusive explanatory paragraphs.
34. **Protocol 34 (Rule 34) — Canonical Identity Provider & Cloud Drive Route Hierarchy:** External identity single-sign-on (SSO) and cloud storage integration endpoints must adhere to a strict, standardized RESTful hierarchy (dedicated initiation, OAuth callback, token exchange, connection status, revocation, and synchronization toggle endpoints). All legacy un-prefixed endpoint routes and unapproved aliases are strictly prohibited.
35. **Protocol 35 (Rule 35) — Single Canonical Identifier per Request Handler (Zero Aliases):** Every controller handler must be defined with a single canonical identifier. Exporting duplicate aliases or compatibility shims for the same handler function is strictly prohibited.
36. **Protocol 36 (Rule 36) — Standardized Controller JSDoc Architecture:** Every controller module and request handler must maintain consistent, standardized JSDoc annotations detailing its functional summary, runtime side effects, canonical HTTP method and route pattern, access classification (public or protected), request and response objects, return contract, and all typed application errors thrown.
37. **Protocol 37 (Rule 37) — Single Source of Truth for Behavioral Directives Naming:** The user directives schema must strictly enforce canonical property naming: an array of behavioral user instructions, an array of negative vocabulary constraints, and a dictionary of phrase replacements. Legacy or speculative naming variants (such as custom instructions) do not exist and must never be introduced into schemas, models, or prompt builders.
38. **Protocol 38 (Rule 38) — Deterministic User Name Derivation from Email:** When extracting identity from an email address upon registration, name parsing must follow deterministic rules: multi-segment local parts split by common delimiters capitalize the first token as the first name and the second token as the last name; single-segment local parts capitalize the first character for the first name and use the complete lowercased token as the last name.
39. **Protocol 39 (Rule 39) — Strict Validation Hygiene & Route-Specific Schema Enforcement:** Every validation schema must explicitly document its input interface, constraints, and target endpoint in JSDoc. Validation schemas must strictly validate only the exact fields expected by that specific operation, rejecting unexpected properties. Permissive catch-all or pass-through validation rules are strictly prohibited.
40. **Protocol 40 (Rule 40) — Mandatory Pre-Handler Request Validation:** Every HTTP endpoint that accepts an incoming request payload (`POST`, `PUT`, `PATCH`) or structured query parameters must mount strict schema validation middleware before invoking its controller handler, guaranteeing that unvalidated or malformed payloads never reach domain logic.
41. **Protocol 41 (Rule 41) — Standardized Leading Adornment Property Pattern:** Form input components with leading icons or adornments must pass them directly via dedicated top-level adornment properties. Deprecated nested input property overrides must never be used on reusable input components.
42. **Protocol 42 (Rule 42) — Exhaustive Three-Tier Account Deletion & Resource Purge:** Permanent account deletion must execute an irreversible three-tier purge: 1) the Data and Storage Tier purges user records, conversation threads, individual messages, local assets, and cloud storage files; 2) the HTTP Session Tier clears all authentication cookies; and 3) the Client State Tier resets all application caches, terminates active sessions, and redirects the user to the landing surface.
43. **Protocol 43 (Rule 43) — Cloud Media Storage Exclusivity & Zero Local Persistent Uploads:** All user avatars, conversational attachments, and generated media artifacts must be persisted directly to dedicated cloud media storage. Storing persistent user media on the local application server filesystem or exposing unauthenticated static upload directories is strictly prohibited. Unconfigured media storage must fail closed with explicit validation errors.
44. **Protocol 44 (Rule 44) — Prohibition of Legacy Compatibility Aliases & Naming Shims:** Retaining historical compatibility aliases, redundant export re-mappings, schema shims, or duplicate facade wrappers is strictly forbidden across the entire codebase. All modules must reference and export canonical identifiers exclusively.
45. **Protocol 45 (Rule 45) — Deterministic Multi-Suite Regression Verification:** Every functional requirement and defect remediation must be validated by deterministic automated test suites executing against a live database replica set. No development phase may be marked complete without passing all backend test suites, zero linter errors or warnings, and zero production bundler build errors.
46. **Protocol 46 (Rule 46) — Agent State Machine Architecture & Human-in-the-Loop Safeguards:** Conversational intelligence must be orchestrated via an explicit state graph compiled with persistent session checkpointing. External, irreversible, or destructive tool mutations (such as cloud uploads, deletions, external messaging, or file generation) must pause execution and emit a human-in-the-loop approval interrupt containing an immutable SHA-256 payload digest. Tool invocations, intermediate reasoning steps, citations, and tool outputs must be preserved as structured polymorphic message parts.
47. **Protocol 47 (Rule 47) — Multilingual Speech Recognition & Synthesis Pipeline:** Speech-to-text transcription must support native regional script recognition with automatic fallback to multimodal audio understanding. Text-to-speech synthesis must provide dynamic voice catalog resolution, phoneme mapping, variable speed control, and client-side audio playback cache management. Browser microphone recording must use standard Web Audio formats with zero input lag and graceful device permission handling.
48. **Protocol 48 (Rule 48) — Modality-Neutral Multimodal Ingestion & Text Extraction:** User turn submissions must be accepted with any valid combination of plain text, documents, images, or voice notes. Uploaded documents must undergo immediate server-side text extraction upon ingestion to enable grounded prompt synthesis and instant document context injection, while raw assets remain immutably persisted in dedicated cloud storage.
49. **Protocol 49 (Rule 49) — Server-Sent Events (SSE) Transport & Monotonic Sequence Typing:** Conversational turn generation must stream over Server-Sent Events with strictly typed event contracts (including text deltas, reasoning steps, tool calls, tool results, interrupts, citations, titling, completion, and error envelopes). Event streams must enforce strictly increasing monotonic sequence numbers and timestamps to enable ordered client assembly and reliable stream resumption.
50. **Protocol 50 (Rule 50) — Headless Chat Component Architecture & Presentation Isolation:** The client chat interface must be built on a headless conversational adapter layer. Active message rendering, token accumulation buffers, and interactive approval cards must reside in localized conversational context, completely isolated from global application store dispatches during live token streaming to guarantee fluid 60fps rendering and instant interaction responsiveness.
51. **Protocol 51 (Rule 51) — Pure Event-Driven Agent Streaming with Typed Projections:** The agent runtime state machine must serve as the sole generation authority using event streaming version contracts that emit typed projections for message tokens, tool invocations, state values, and final outputs. The server layer operates as a pass-through transport streaming these events over the wire, while client stores receive zero dispatch churn during active chunk buffering.
52. **Protocol 52 (Rule 52) — Tiered Conversational Memory Architecture:** Conversational context must implement a formal two-tiered memory architecture: short-term memory is managed via persistent session checkpointers scoped to thread identifiers, while long-term cross-session knowledge and preferences are maintained via a persistent semantic store bridged directly to the user's authoritative behavioral directives.
53. **Protocol 53 (Rule 53) — Dual Execution Pathways for Interactive vs Non-Streaming Workflows:** AI execution must maintain two distinct pathways: interactive conversational turns strictly stream incremental event deltas, whereas non-streaming, transactional, or offline workflows (such as conversation auto-titling, summary generation, or background evaluations) execute via direct unary invocation.
54. **Protocol 54 (Rule 54) — Dynamically Assembled System Prompt Invariant:** System instructions must never be hardcoded into agent definitions. Prompts must be dynamically assembled per turn by compiling current multi-calendar temporal context, authoritative user behavioral directives, negative vocabulary constraints, and user-configured persona settings into a dynamic system prompt parameter passed directly to the runtime.
55. **Protocol 55 (Rule 55) — Pristine Multimodal Asset Preservation:** Original binary assets (images, documents, audio recordings) stored in cloud storage are immutable and must never be altered or overwritten. Visual assets must be passed natively into multimodal model context, documents must be provided as read-only grounded text context blocks or queried through dedicated retrieval tools, and audio must be transcribed via speech-to-text while keeping the original acoustic recording intact.
56. **Protocol 56 (Rule 56) — 100% Dynamic Model-Driven Execution State Tracking:** Static or hardcoded status labels are strictly abolished. Conversational timeline indicators must dynamically reflect the model's real-time cognitive activity by streaming live thought clauses during deliberation, displaying contextual descriptions extracted directly from tool arguments during execution, and surfacing structured data summaries upon completion.
57. **Protocol 57 (Rule 57) — Mandatory Utilization of Workspace Skills, Plugins & Protocol Tools:** AI agents operating in this repository must actively discover, invoke, and leverage all specialized skills, plugins, rules, and model context protocol integrations available under the workspace agent directory (`.agents/*`). Agents must utilize these domain skills—including agent framework architectures, persistence backends, orchestration patterns, planning methodologies, testing disciplines, and systematic debugging workflows—before implementing solutions, ensuring every task is executed with specialized domain intelligence and rigorous engineering standards.
58. **Protocol 58 (Rule 58) — Production-Grade Conversational Architecture, Strict LangChain Runtime Authority & Full-Fidelity UI Parity:**
    - **Foundational Purpose & Elimination of Historical Defects:** The platform is engineered as a clean-slate re-implementation to preserve all proven capabilities of previous iterations while permanently eradicating their fatal architectural flaws. The system strictly forbids: 1) unbounded embedded message arrays that cause database degradation and memory bloat; 2) unauthenticated static exposure of private user media; 3) array-positional or client-inferred retry and branch identities that corrupt conversation trees; 4) raw model chain-of-thought token leakage into public message bodies; 5) transient in-memory file registries; and 6) competing state listeners fighting over streaming chunks.
    - **Strict Backend Agent Authority via LangChain & LangGraph:** Conversational intelligence, reasoning, tool execution, and memory in the backend must be orchestrated exclusively through native LangChain and LangGraph framework constructs:
      - **State Machine Runtime:** The core conversational flow must be structured as a compiled state graph with explicit nodes for model reasoning, tool execution, human-in-the-loop approvals, and error recovery.
      - **Tool Execution & Structured Schemas:** All agent capabilities must be defined as native LangChain tools with strictly typed input schemas and predictable execution boundaries.
      - **Durable Checkpointing & Tiered Memory:** Conversation threads must be persisted via native checkpointers mapped to unique thread identifiers, while cross-thread long-term memory is maintained via a semantic store bridged to authoritative user directives.
      - **Pure Event-Driven Generation (v3 Projections):** The runtime must stream exclusively via LangChain event streaming version 3, exposing discrete projections for message deltas, tool calls, and state snapshots. The HTTP server operates strictly as a transparent transport layer forwarding these events over Server-Sent Events.
    - **Full-Fidelity Frontend Awareness & Complete Event Parity:** The frontend conversational interface must maintain 1-to-1 parity with the backend agent, capturing, processing, and rendering every single event emitted during execution with zero unhandled data or dropped telemetry:
      - **Live Token & Thought Streams:** Incrementally render token chunks and route model deliberation tokens into dedicated, collapsible reasoning accordions rather than message text.
      - **Execution Timeline & Step Tracking:** Display dynamic step transitions (start, progress, completion, failure) matching the agent's real-time state machine transitions.
      - **Tool Calling & Structured Output Cards:** Render tool invocation cards showing active arguments, execution spinners, and structured tool result representations.
      - **Human-in-the-Loop Approval Gates:** Present interactive approval interfaces displaying exact tool parameters and immutable security digests, pausing the UI until the user explicitly confirms or rejects the action.
      - **Citations & Multimodal Assets:** Render grounded references, source links, visual media, and generated document cards directly in the message flow.
      - **Terminal Completion & Error Envelopes:** Handle run completion, token metrics, and structured error states gracefully without losing prior turn context.
    - **Industry-Standard Decoupled State Architecture (Benchmark: ChatGPT, Gemini, DeepSeek):** To achieve the fluid responsiveness of production AI systems, state ownership must be strictly partitioned to guarantee zero state and store conflicts:
      - **Global State Boundary:** Global application state strictly manages RESTful entity caching, authentication session identity, and navigational thread drawer metadata (titles, pinned status, pagination cursors). Global state must NEVER subscribe to, buffer, or receive action dispatches for incremental streaming tokens.
      - **Conversational Runtime Boundary:** The dedicated headless chat adapter context is the single authoritative owner of the active conversation turn, live token accumulation, real-time typing buffers, thought disclosure accordions, and interactive approval cards.
      - **Zero Conflict Contract:** No two stores, adapters, or listeners may ever compete for the same message state. Streaming chunks must bypass global state entirely and render via localized high-frequency subscribers to guarantee zero re-render cascades, 0ms input latency, and 60fps interface fluidity.

60. **Protocol 60 (Rule 60) — Strict Validated Data Access via `req.validated`:** Request controllers, domain services, and downstream request handlers must strictly consume validated and sanitized payloads from `req.validated.body`, `req.validated.query`, and `req.validated.params` populated exclusively by schema validation middleware. Directly accessing unvalidated `req.body`, `req.query`, or `req.params` in controllers is strictly prohibited, guaranteeing that unparsed, unvalidated, or malicious client inputs never reach domain logic.
61. **Protocol 61 (Rule 61) — Pure Cookie-Based Authentication Transport & Zero Token Exposure in JSON Payloads:** Session credentials (access tokens, refresh tokens) must be transported exclusively via secure, `HttpOnly`, `SameSite=Lax/Strict` cookies. Authentication controllers (`register`, `login`, `refreshToken`, SSO callback) and error handlers must NEVER expose, return, or mirror token strings (`accessToken`, `refreshToken`) within JSON response bodies. Downstream services and middleware must resolve session identity exclusively from `req.cookies`. Interactive test suites (`.http` / `.rest`) and client adapters must rely on standard cookie persistence, never expecting bearer tokens in JSON response bodies.
62. **Protocol 62 (Rule 62) — Defensive Error Handling & Standardized Envelope Delivery for Malformed Client Payloads:** The server application must defensively intercept malformed client payloads, body-parser syntax errors (e.g. malformed JSON strings, unexpected trailing characters, truncated streams), and encoding failures at the middleware boundary, returning a standardized HTTP 400 (`MALFORMED_JSON` / `BAD_REQUEST`) JSON error envelope. Unhandled 500 exceptions, stack traces, or process crashes from malformed client input are strictly forbidden. All interactive test suites (`.http` / `.rest`) must format request bodies with clean JSON syntax free of foreign script blocks or unseparated trailing characters to ensure deterministic test execution.
63. **Protocol 63 (Rule 63) — Multi-Provider AI Foundation Model Authority & Explicit Namespacing:** Conversational and agentic intelligence across backend and frontend runtimes must support multi-provider AI architectures with explicit namespacing (`google` and `addis`). Provider definitions, model rosters, base URLs, authentication headers, and feature support matrices (such as `thinkingBudget` support for Google vs absence in Addis) must be centralized in constants with 1-to-1 parity between backend and client. Foundation models must be mapped strictly to their authoritative providers (`gemini-3.1-flash-lite`, `gemini-3.8-flash`, `gemini-3-flash-preview` to Google; `addis-1` to Addis AI). Default provider and model configurations must be persisted in user settings and validated via strict Zod enumerations.
64. **Protocol 64 (Rule 64) — Strict BYOK Production Isolation & Safe Development-Only Credential Fallbacks:** Third-party API keys (Gemini, Addis AI) and connector credentials (Telegram, Cloudinary) supplied in server environment variables are exclusively for local testing and development environments (`NODE_ENV === 'development'`). In production environments, server `.env` files must NEVER contain shared API keys or connector secrets; credentials must be supplied exclusively by individual users via Bring-Your-Own-Key (BYOK) interfaces and envelope-encrypted at rest (AES-256-GCM). The server configuration must ensure all development-only keys are optional with safe fallback defaults so that their absence in production never crashes the process. In production, the system must warn if a dedicated `ENCRYPTION_KEY` is not explicitly set.
65. **Protocol 65 (Rule 65) — Universal User Terminology & Absolute Prohibition of Role-Specific "Supervisor" Nomenclature:** The platform is a Personal AI Agent designed for individual users. All domain models, controller handlers, service methods, validation schemas, route documentation, JSDoc annotations, and UI display labels must universally refer to the authenticated entity as "user" (e.g. `userInstructions`, `user directives`). The term "supervisor" represents a legacy, over-specified organizational artifact and is strictly prohibited across all code, tests, documentation, and metadata.

Integrations must implement uniform RESTful lifecycle endpoints: status inspection (`GET /integrations/:service/status`), credential verification (`POST /integrations/:service/verify` where applicable), credential attachment (`PATCH /integrations/:service/connect`), synchronization toggle (`PATCH /integrations/:service/toggle`), and credential revocation (`POST /integrations/:service/disconnect`). Integration toggle requests across all services must share a unified, strictly validated boolean payload schema (`toggleIntegrationSchema`).
67. **Protocol 67 (Rule 67) — Prohibition of Trivial Primitive Constants & Meaningless Exported Fallbacks:** Constants modules must strictly define domain boundaries, enumeration rosters, validation thresholds, timeouts, regex patterns, and route endpoints that convey meaningful domain rules. Exporting trivial primitive placeholders or empty string fallbacks (such as `DEFAULT_POSITION = ''`) provides zero architectural value, pollutes module namespaces, and introduces false dependencies. Default values for optional entity attributes must be specified directly in database schemas and domain services.
68. **Protocol 68 (Rule 68) — Dual-Modality Automated & Interactive Test Architecture with Guaranteed Teardown Hygiene:** Testing across all project phases must enforce a dual-modality architecture segregated cleanly into dedicated directories: 1) Interactive Human Modality (`tests/http/*.http`) for visual, on-demand vertical-slice testing via REST Client; and 2) Automated Headless Modality (`tests/integration/*.test.js`) executed via Node.js native test runner (`node:test`, `node:assert/strict`) without manual intervention or external mocking libraries. Automated tests must be runnable individually and collectively via standardized workspace scripts (`npm test`, `npm run test:phase1`, `npm run test:phase2`, `npm run test:all`). Temporary verification scripts (such as `verifyEndpoints.js`) are strictly prohibited in production.
69. **Protocol 69 (Rule 69) — Pure Provider-Namespaced AI Foundation Models & Clean Platform Defaults:** Foundation model constants across backend and client runtimes must enforce strict provider namespacing at the object root. The `AI_MODELS` dictionary must strictly expose provider keys (`[AI_PROVIDERS.GOOGLE]`, `[AI_PROVIDERS.ADDIS]`) mapping to provider-specific configuration objects containing `DEFAULT`, `PRO`, `FALLBACK`, and `MODELS` rosters. Mixing top-level fallback or default aliases (`DEFAULT`, `PRO`, `FALLBACK`, `REGIONAL`, `SUPPORTED`) directly inside the root `AI_MODELS` object is strictly prohibited. Chat runtime defaults (`CHAT_CONSTANTS`) must cleanly reference platform-level defaults (`DEFAULT_PROVIDER: AI_PROVIDERS.GOOGLE`, `DEFAULT_MODEL: AI_MODELS[AI_PROVIDERS.GOOGLE].DEFAULT`, `SUPPORTED_MODELS: SUPPORTED_AI_MODELS`).
70. **Protocol 70 (Rule 70) — Unified Agent Configuration & BYOK Route Consolidation:** Bring-Your-Own-Key (BYOK) credential management for foundation model providers (Gemini, Addis AI) must be unified directly into the agent configuration resource lifecycle (`/api/v1/users/agent-config`). Standalone `/api-keys` routes and fragmented controllers represent anti-patterns that decouple credential provisioning from the AI runtime settings that consume them. Updating API keys is executed via an optional, strictly validated `apiKeys` sub-object within `updateAgentConfigSchema` on `PATCH /api/v1/users/agent-config`. Services must envelope-encrypt non-empty strings (AES-256-GCM), update boolean presence flags (`hasGeminiKey`, `hasAddisKey`), clear credentials when set to `null` or empty strings, and preserve existing credentials when the `apiKeys` sub-object or individual keys are omitted. Key secrets are never returned in response payloads. Standalone `PATCH /api-keys` endpoints are permanently purged (returning 404).
